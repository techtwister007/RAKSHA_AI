2RAKSHA in one page

In plain words

RAKSHA is a self-driving security mechanic for software. You give it a program's source code. It finds weaknesses, proves each one is real by making it happen in a safe box, writes a fix, and proves the fix works with five independent checks. It hands you a sealed receipt for every claim. It does all of this offline, with the network cable pulled, because Army networks are sealed.

  • Find: fast checks that need no compiling, plus deep checks that run the code with thousands of test inputs.
  • Prove the weakness: nothing is reported unless it can be reproduced. "No reproducer, no report."
  • Fix: a ladder of fixers from cheapest to most expensive: known fix patterns, past fixes, then an AI model.
  • Prove the fix: a five-check gate decides. The AI never decides anything.
  • Show it: an offline console for operators and commanders, in English and Hindi, with signed reports a judge can re-check on their own laptop.
  • Remember: every project gets an ID and a versioned, colour-coded history; recurring faults become proposed guidelines.
Key takeaways
  • RAKSHA shows proof, not opinions.
  • It works offline, on unfamiliar code, in several languages.
  • Humans keep authority: rules of engagement decide what it may do on each system.
Part I

The problem and the aim

What the competition asks for, why it is hard, and what RAKSHA promises in return.

3The competition

AI Kavach is a challenge to build working technology for real defence and national-security problems. The task for this track, in the organisers' words, is a cyber-reasoning system that autonomously finds a vulnerability, patches it, and proves the fix holds, pitched to run against customised infrastructure of the Indian Armed Forces.

Terms explained

Cyber-reasoning system (CRS): a program that reasons about the security of other programs by itself. Vulnerability: a weakness in software that someone could misuse. Patch: a change to the code that removes the weakness. Autonomously: without a human in the loop during the find-fix-prove cycle. Air-gapped: physically disconnected from any outside network.

How it is judged

StageWhat is scored
Shortlisting (5 slides)Resource utilisation · novelty of idea · how lightweight the solution is
Grand Finale (36-hour build)Performance (bugs found and patched) · speed · precision (how often it is right) · functionality (the full loop, autonomously) · scalability (many targets and languages)

4The problem

Finding and fixing weaknesses in software is slow, skilled work. Army software adds three hard conditions:

  • Unfamiliar code. Custom systems no public tool has ever seen, in several programming languages.
  • Sealed networks. No internet, so no cloud AI and no online databases at the point of use.
  • High stakes. A wrong "fix" on a mission system can do more harm than the weakness. Every claim must be checkable.

5Why today's AI tools fall short

  • They guess. General AI models produce plausible fixes that are often wrong; published evaluations show frontier models failing a large share of real repair tasks.
  • They need the internet. The strongest models run in the cloud, which a sealed network forbids.
  • They give no proof. A static scanner says "this line might be risky". A commander cannot act on "might".
Term explained

Static scanner: a tool that reads code without running it and flags patterns. Fast, but it cannot show that a problem really happens.

6Our aim and promise

In plain words

Find real weaknesses in code nobody has seen before, fix them, and hand over evidence anyone can re-check, all offline, with humans in charge of what gets applied.

The promise rests on one design choice: the AI model is an intern, not the judge. It may suggest. Deterministic checks decide.

Term explained

Deterministic: gives the same answer every time for the same input. A check that cannot be talked out of its answer.

7Scope

In scope
  • Source code in C/C++, Python, Java, JavaScript/TypeScript, Go and Rust (deep checks)
  • Any language for build-free checks (dependencies, secrets, crypto, configuration, API specs, binaries, git history)
  • Proving, fixing and re-proving; signed evidence; reports for operators and commanders
  • Offline operation on a single sealed machine
Out of scope
  • Attacking live systems or networks: RAKSHA only works on code handed to it, inside its own sandbox
  • Applying fixes to production by itself on critical systems (humans approve)
  • Claiming a system is "secure": RAKSHA reports what it found, never the absence of problems

8Ground rules we never break

  1. No reproducer, no report. Every reported weakness can be made to happen again.
  2. The model never decides. It proposes; the five-check gate decides.
  3. Presence, never absence. RAKSHA says what it found. It never says "secure".
  4. Nothing leaves the box. No code, finding or report goes over a network. This is measured, not promised.
  5. Every number is measured or empty. If something was not measured, the screen shows a dash, never a made-up figure.
  6. Untrusted code runs only in the sandbox.
  7. Zero false alarms on clean controls. Deliberately clean code must produce no findings, checked after every change.
Term explained

Reproducer: the exact input that makes the weakness happen, kept so anyone can replay it. Sandbox: a sealed box (a container with no network) where untrusted code runs so it cannot touch anything else.

Part II

The solution at a glance

The core idea, the life of one finding, what is new, and who uses it.

9The core idea

RAKSHA wraps an AI model inside a frame of hard, checkable tools. Three kinds of work happen in order: find (gather evidence a weakness exists), fix (propose changes, cheapest first), prove (judge each change with checks that cannot be argued with). Only proven results reach a person.

10A finding's life story

  1. Suspected: a lane notices something. It stays private.
  2. Confirmed: the reproducer makes it happen again, observed by an oracle (Chapter 17).
  3. Patched: a candidate fix is applied to a scratch copy and put on trial.
  4. Verified: the fix passed all five gate checks (Chapter 21). If no candidate passes within three rounds, the finding is report only: proven, but referred to a human.

Part II-B

The journey, end to end

One example codebase followed through every stage of the pipeline: what happens inside, how it moves to the next stage, and what you see on the console meanwhile.

WThe example

A unit hands over a small project called signals-parser on a USB stick. It contains:

  • src/tlv.c: a C function that reads incoming messages. It copies each message into a fixed 16-byte buffer without checking the length (a real weakness: a longer message overwrites memory next to the buffer).
  • config/app.properties: a database password written in plain text.
  • requirements.txt: a Python helper that pins pyyaml==5.3.1, a version with a published advisory.

The asset registry lists signals-parser as mission-critical, mission function "message parsing", owner unit "Signals". The finale box has a C compiler and no model server running (so we can see the AI-free path).

In plain words

Three different problems in one project: a memory bug that only shows up when the code runs, a leaked password, and an old library. Watch how each is handled differently, and what a person sees at each step.

1Media accepted

You do: on the console's Demo Beats screen, type the USB path (for example /media/usb/signals-parser) and press Ingest. (At the finale, targets placed in /targets are picked up the same way at start.)

Inside: the intake desk checks the path is a real folder under an allowed media root, and that no other intake is running. If either check fails you get a one-line reason and nothing else happens.

You see: "accepted", and a clock "time to first finding: 0.3 s and counting".

Moves on when: the checks pass; a background worker takes over so the console never freezes.

2Staged as data

Inside: every file is copied into a private scratch folder, as plain data. Shortcuts and special files are skipped and counted. Execute permissions are dropped, so nothing on the stick can be run by accident. Limits stop a huge or hostile medium (file count, total size, size per file, folder depth); if a limit is hit the copy stops there and the record says "truncated".

You see: event log line "signals-parser: staged 14 files (9,812 bytes); 0 links skipped".

3Project identified

Inside: RAKSHA looks in its project store. No project called signals-parser with this file layout exists, so it mints PRJ-signals-parser-…. It looks the name up in the asset registry: mission-critical, Signals, "message parsing". That tier caps the rules of engagement at R1 (recommend): RAKSHA may prove and draft fixes, but applies nothing.

You see: nothing yet on the board; the ID appears with the first report (Stage 17).

4Build-free lanes run

Inside: every file is read once, by every lane at the same time:

  • Secrets lane matches db.password=… in config/app.properties. It records the rule, file and line, and a masked preview (only the first and last characters). Its reproducer is a re-check command: run the same detector on the same line again.
  • Supply lane parses requirements.txt, finds pyyaml 5.3.1, and checks the offline advisory database: it is inside a known affected range, fixed in 5.4. It also checks whether the code actually imports it (reachability) and prepares a version-bump patch.
  • Crypto, config, API and binary lanes find nothing here.

Because each match can be re-run exactly, these two findings go straight to CONFIRMED.

You see: a new amber card on the Mission Board, "signals-parser · build-free mode, still finding". Event log: "build-free scan complete (2 findings, 2 proven)" and "first finding on the board 3.9 s after the media went in". The clock stops.

5Findings annotated and ranked

Inside: duplicates from different lanes are merged. Each finding gets its asset tier, a CVSS 3.1 score, ATT&CK and D3FEND labels, and a place in the risk register (severity × mission tier × known-exploited data).

You see: Live Pipeline shows two findings in the CONFIRMED column; the risk register lists them in fix-first order.

6Deep lane: finding an entry point

Inside: RAKSHA reads the C source (never running it yet) looking for functions that take input, here parse_record(const char *data, int len). It scores candidates by shape and name. With a model server running, the model would also help rank them; here the deterministic ranking is used.

You see: "signals-parser: looking for an entry point to fuzz (no harness shipped)".

7Harness written and checked

Inside: RAKSHA writes a small C driver that feeds bytes to parse_record, using random file and symbol names for this run. It compiles the driver with the target code and the memory-error detector, inside the sandbox. A two-part quality check follows: it must compile, and it must run one ordinary input cleanly. A driver that fails is discarded and the next entry point is tried.

You see: "harness synthesized for parse_record (c/c++); quality gate passed".

8Fuzzing in the sandbox

Inside: the driver starts once and then forks a fresh child process for each input, so each test is isolated but fast. Inputs are generated by small changes to a seed set (flip a byte, grow, shrink, repeat, insert boundary values). Each child has no network and is cut off after 2 seconds if it hangs. The search stops when a crash appears or the budget is spent.

You see: Scorecard execution count climbing; the target card stays amber.

9The alarm rings

Inside: one input longer than 16 bytes makes the copy write past the buffer. AddressSanitizer, the memory alarm compiled into the build, stops the child and prints exactly what happened and where: stack-buffer-overflow in parse_record, src/tlv.c line 11. The finding is born as SUSPECTED.

10Confirming it is real

Inside: before anything is reported:

  1. The input is replayed in a fresh one-shot run; the alarm must ring again (twice).
  2. Attribution: if the crash were inside RAKSHA's own driver, it would be dropped. It is in tlv.c, the target's code.
  3. Minimise: the input is shrunk to the smallest one that still rings the alarm, so the evidence is easy to read.
  4. Contract check: if the function stated a precondition no real caller can break, it would stay suspected with the reason. Not the case here.

Status becomes CONFIRMED, and the reproducer is stored with a fingerprint.

You see: event log, highlighted: "signals-parser: CWE-121 confirmed at src/tlv.c:11; reproducer of 17 bytes replays". The finding appears in Finding Detail.

11The repair ladder and patch hygiene

Inside:

  1. Template: the "bound the copy to the buffer size" template matches this shape and produces a two-line change.
  2. Fix memory: checked for a past proven fix of the same kind (none yet). With a model server, a model candidate would come next, only if cheaper rungs fail.
  3. Hygiene: the candidate touches only src/tlv.c (the fix site), adds 2 lines (limit 150), and adds no command, network or code-loading call. Admitted.

Status becomes PATCHED (on trial).

You see: the Live Pipeline card moves to PATCHED.

12The five-check gate

Inside: two scratch copies are built in the sandbox, the original and the patched.

CheckWhat happensHere
1 COMPILESBoth copies buildpass
2 POV_DEADThe 17-byte reproducer runs on the patched copy; the alarm must stay silentpass
3 DIFFERENTIAL_CORPUSNormal inputs run three times on the original (unstable ones set aside), then on both copies; outputs must match exactly; the project's own tests must pass; it must not be much slowerpass: 5 inputs identical, tests pass
4 COVERAGE_HELDThe patched line must still be reached by normal inputs (the feature was fixed, not deleted)pass
5 CLEAN_REFUZZ24 close variations of the reproducer and a fresh fuzzing pass on the patched copy; the same weakness must not return, and no new kind of crash may appearpass

You see: in Finding Detail, the gate strip fills with five green ticks, one by one. Had any check failed, it would turn red with the reason, and the ladder would try the next candidate (up to three rounds).

13Extra proofs

Inside: the fix is re-checked on an optimised release build; the Z3 solver proves the new bound always holds; undoing the patch is shown to restore the exact original bytes. Each proof is added to the record as extra evidence.

14The red team

Inside: an independent round tries to show the fix does not hold, with its own wider set of test inputs (including many input lengths) for a few seconds. It finds nothing. Had it succeeded, the record would show the fix as broken.

You see: "independent red team held; no input broke it (277 attempts)". Status: VERIFIED.

15Authority: who may apply it

Inside: signals-parser is mission-critical, so the fix is recommend only: it needs two human approvals and is never applied by RAKSHA.

You see: in Finding Detail, the split-screen replay (original: alarm rings; patched: silent), the two-line patch, the gate record, the red-team result, and Approve / Reject buttons with "2 signatures required". The Commander's Brief tab has the same finding as a short staff paper, in English or हिन्दी.

16Evidence sealed, memory updated

Inside: an evidence bundle is written and signed for each of the three findings. Every step above is in the hash-chained journal. The proven fix is stored in fix memory, and a vaccine sweep checks other codebases for the same mistake.

You see: Evidence Vault lists the three; pressing Verify re-checks every byte. The Scorecard updates precision, fixes, timings and model calls (0).

17Report v1

Inside: the first signed project report is written:

  • Needs a human (3): rotate the database password (with a checklist); approve the prepared pyyaml upgrade (it needs a build); approve the proven memory fix (recommend-only asset).
  • Posture score, exposure clocks started, the secret recorded as exposed, the library inventory and attack surface noted.

You see: Projects screen: signals-parser · v1 · score · 3 need you. One-page summaries in English and Hindi. The readiness certificate is refused while a critical item is open.

18The owner acts, and RAKSHA checks

The owner: applies the approved patch, rotates the password and removes it from the file, bumps pyyaml to 5.4, and marks the items done. Then runs signals-parser again.

Inside: the same pipeline runs. The secrets and supply lanes no longer match, which is itself proof. The memory bug is not re-found. Report v2 is written, chained to v1, and the marked-done items are re-checked rather than trusted.

You see: report v2: ✓ fixed password, ✓ fixed pyyaml, ? not re-found memory bug (shown honestly: a crash not seen again is not counted as proven fixed unless its old reproducer is replayed), "confirmed closed by this run" for each marked item, the trend line, and now a readiness certificate.

19Learning, quietly

The two reports are added to the learning history: one memory fault, one secret, one dependency, owner unit Signals. If the same family keeps recurring across projects, a draft guideline appears on the Learning screen for ACG to approve. From now on, the pre-merge check can stop the same mistake before it ships.

When things go differently

  • No crash found in the budget: the card stays amber; the build-free findings stand; the record says the deep lane found nothing (never "secure").
  • No fix passes the gate: after three rounds the finding is REPORT ONLY, with the reason for each refusal, and goes on the needs-a-human list.
  • The red team breaks a fix: the record shows it broken; the fix is not offered for approval.
  • A toolchain is missing: that language's deep lane is skipped and says so; build-free lanes still run.
  • With a model server: stages 6 and 11 can call the model for ranking and fix candidates; everything after it is unchanged, because the gate decides.
Key takeaways
  • Fast proven findings in seconds, deep ones as the fuzzing finds them.
  • Every stage leaves a visible trace on the console and in the journal.
  • Nothing is applied without the authority the asset allows, and every claim can be replayed.

Part III

The architecture, layer by layer

How code goes in, how weaknesses are found and proven, how fixes are made and judged, and how everything is kept sealed and recorded.

13The big picture

For engineers

Python 3.11, standard library only at run time; optional extras (the SMT solver) degrade to a documented fallback when absent. The orchestrator (raksha/orchestrator.py) holds the live session; the console is a stdlib HTTP server (console/server.py). Every spawn of target code goes through one door, raksha/sandbox.py.

14Getting code in

Code arrives three ways: mounted at start (the finale's /targets folder), ingested on the console from a judge's USB media (bring your own target), or scanned from the command line.

Built · safe intake
  • Only paths under allowed media folders are accepted.
  • The tree is copied as plain data into a private scratch folder, within limits (files, total size, size per file, folder depth).
  • Shortcuts (symlinks), devices and other special files are skipped and counted, never followed.
  • Scanning happens off to the side and is merged into the live board in one step, so the console never freezes or shows half a result.
  • Time to first finding is measured and shown live (4 seconds on the demo estate).
Term explained

Symlink: a file that points to another file elsewhere. A hostile medium could use one to trick a tool into reading outside the folder, so RAKSHA refuses them.

15Build-free lanes: checks that need no compiling

In plain words

Many real weaknesses can be proven just by reading files: an old library with a known flaw, a password left in a config file, encryption turned off. These checks work on any language, need no build, and take seconds.

Dependency: a library your code borrows. Advisory: a public notice that a version of a library has a flaw. RAKSHA carries an offline copy of the OSV advisory database. SBOM (software bill of materials): an ingredients list of the software.

Each build-free finding has a deterministic re-check: python -m raksha secret-match … and similar commands re-run the same detector on the file, so a judge can replay it.

16Deep lanes: running the code to find real crashes

In plain words

RAKSHA finds the functions in the code that take input, writes a small test driver for each, and feeds it thousands of varied inputs inside the sandbox. When one input makes the program misbehave, that input becomes the reproducer.

Terms explained

Fuzzing: automatically trying huge numbers of varied inputs to make a program fail. Harness: the small driver that feeds inputs to the code under test. Synthesized harness: one RAKSHA writes itself, so targets that ship no test driver can still be tested.

LanguageHow it is testedNeeds

Each input runs in a short-lived child process, cut off after two seconds if it hangs, so the search never stalls. Crashes are re-checked twice, shrunk to a minimal input, and attributed: a crash inside RAKSHA's own driver is dropped, never reported.

Partial · depends on toolchains

A language's deep lane runs only if its toolchain is installed. The current sealed image carries gcc, JDK and Maven; Node, Go, Rust and clang are a team step (Chapter 54).

17Oracles: the alarm bells

In plain words

An oracle is an alarm that rings only when something genuinely bad happens, such as a write past the end of a buffer. Because the alarm is observed, the finding is a fact, not a guess.

Term explained

CWE (Common Weakness Enumeration): a standard numbering of weakness types, e.g. CWE-121 stack overflow, CWE-78 command injection. Each oracle labels what it saw with a CWE.

18The finding record

Every lane, in every language, produces the same record. That is why one gate, one console and one report format serve everything.

For engineers · key fields

oracle, bug_class (CWE), language, target, severity, frames (stack), fix_site_set (ranked places to fix), reproducer (bytes + replay command + hash), replay_before/after, gate (five results), patch_diff, repair_lane, red_team, roe_level, plus proofs (bound, reachability, rollback). Status changes are guarded: a record cannot jump to VERIFIED without the gate history behind it. Source: raksha/finding.py.

19The repair ladder

Fixers are tried cheapest first. Each candidate goes to the gate; the first that passes all five checks wins (or, with the frontier on, the best of several that pass).

  1. Templates (no AI): known fix shapes, e.g. "bound this copy to the buffer size", "pass arguments as a list instead of a shell string".
  2. Fix memory (no AI): a fix proven earlier for the same kind of weakness, re-applied; it can even carry a fix idea across languages.
  3. AI model: proposes a patch, optionally with a test; if the gate refuses it, the model gets the gate's reason and one more try.
  4. Mitigation: a blunt but safe floor, labelled as such.

At most three rounds. If nothing passes, the finding is report only and the record says exactly which check refused each attempt.

Built · measured

On the demo set, 100% of verified fixes so far cost zero AI calls (templates and memory). The mutation factory shows templates fix 8 of 8 disguised variants of known bugs (it was 6 of 8 until the local-model benchmark exposed a template gap, now closed).

20Patch hygiene: refusing unsafe fixes before they are tried

In plain words

Before a fix is even built, three rules check it. A fix may only touch the files where the weakness is; it must stay small (at most 150 added lines); and it may not introduce anything that runs commands, opens network connections or loads code, unless the original already did. A fix that breaks a rule is refused and the refusal is recorded.

This matters because an AI model reads the target's code, and that code could contain text designed to steer the model. Hygiene stops a steered fix before it is ever run.

21The five-check gate

In plain words

The gate is a strict examiner. It asks five questions about a fix. Only a fix that passes all five is called verified.

#CheckThe questionCatches
1COMPILESDoes the original build, and does the patched one?broken fixes
2POV_DEADDoes the original reproducer no longer trigger the alarm?fixes that do not fix
3DIFFERENTIAL_CORPUSDo normal inputs give exactly the same output as before? Do the project's own tests pass? Did it get much slower?fixes that break normal behaviour
4COVERAGE_HELDIs the fixed code still reached by normal inputs?"fixes" that just delete the feature
5CLEAN_REFUZZDo close variations of the reproducer, and a fresh fuzzing pass, still trigger the same weakness?shallow fixes that only block the one known input
Terms explained

POV (proof of vulnerability): the reproducer. Corpus: a collection of normal test inputs. Coverage: which lines of code an input actually runs. Differential: comparing before and after on the same inputs.

The gate fails closed: if a target cannot run a check (for example, no fuzzing possible), the fix is not verified and the record says why. A fix that passes all checks on too little evidence is also held back as report only.

22Extra proofs

  • Deployment twin: the fix is re-checked on an optimised release build, not only the instrumented test build.
  • Bound proof: for size-limit fixes, a mathematical solver (Z3) proves the new limit always holds.
  • Reachability proof: the solver shows the bad state was reachable before the fix and is not after.
  • Rollback proof: undoing the fix returns the code to exactly its original bytes.
  • Regression test: a test is kept only if it fails before the fix and passes after.
Term explained

SMT solver: a program that proves or disproves mathematical statements about code automatically. These proofs are extra evidence; they never replace the gate.

23The red team

In plain words

After the gate says yes, an independent checker tries to show the fix still does not hold, using a wider and differently chosen set of test inputs than the gate used. If it succeeds, the fix is marked broken on the record. The red team can only ever take a "yes" away; it can never give one.

The "it says no" demo beat shows this live: a weak fix passes the gate, and the red team catches it.

24The AI models

Where the model helpsWhere it is kept out
Ranking which functions to test firstDeciding whether a weakness is real (oracles do)
Proposing repair candidates and testsDeciding whether a fix works (the gate does)
Advisor, judge and red-team roles whose disagreements are shownAnything leaving the box (sealed mode refuses remote endpoints)
Similarity search over past fixesSeverity scores (computed from the record)
Partial · model server

RAKSHA talks to any OpenAI-compatible model server. The finale design serves a ~32B coding model with vLLM on the box's GPU. No model is bundled in the repository; without one, RAKSHA runs model-free and still finds and proves, fixing only the shapes its templates and memory know.

Built · benchmarked with a local model

Four runs with Qwen2.5-Coder-7B on CPU (docs/model-benchmark.md) found six weaknesses in the model path, all now fixed: patch hygiene refused the standard command-injection fix; small models write malformed diffs (now they may send "search / replace" edits and RAKSHA writes the exact diff); the prompt contradicted the fix; the model server returned one candidate instead of three; empty patches reached the gate; and a template gap meant two variants were never fixed. The 7B model itself added no fixes; the finale design uses a ~32B model on the GPU.

Built · the model path checked on its own

To separate "the model is weak" from "the pipeline loses good answers", the fix templates were switched off and a stand-in model gave answers written in advance (scripts/model_lane_check.py). Correct fixes: 8 of 8 proven through the gate. Plausible but wrong fixes (a bound that is too loose, a blocklist, shell quoting, eval): 0 of 8. The check exposed one more flaw, now fixed: a model that copied a line without its trailing comment had every correct C fix thrown away before the gate.

Terms explained

LLM (large language model): an AI that writes text and code. vLLM: software that serves a model on a GPU. Sealed mode: a setting that refuses any model endpoint that is not on the box itself.

25The evidence bundle

Every reportable finding gets a sealed folder: the proof record, the replay script and reproducer, the patch and rollback script, the regression test, plain-language report, Commander's Brief, environment details, a provenance statement and a signature over all of it.

In plain words

A bundle is a receipt. Change one byte anywhere in it and verification fails. A judge can check it on the console's Evidence Vault, or on their own laptop with the verifier media.

Built · signing

Bundles are signed with HMAC-SHA256 using a deployment key the installer generates on the box (never shipped, never committed); without one, the published demo key is used and every bundle says so. When a cosign key pair is provisioned, every bundle also gets a public-key seal that anyone can verify but no one without the private key can forge. Post-quantum signatures are added when the library is present.

26The session journal

Every event is appended to a diary in which each line carries a fingerprint of the line before it. Change or delete any line and the chain breaks. The journal lets a crashed run resume exactly, powers the live event log, and feeds the time-lapse that replays a whole run minute by minute.

Term explained

Hash chain: a list where each entry includes a fingerprint (hash) of the previous one, so tampering anywhere is detectable.

27Sandbox and air gap

  • One door: every launch of target code goes through raksha/sandbox.py; a test forbids any other route.
  • No network, fewer powers: the sandbox container has no network and drops system capabilities; a setting refuses to run target code at all without it.
  • Air-gap guard: an automated check proves RAKSHA's own code contains no network client outside the single local model connector, and the console loads nothing from outside.
  • Live egress counter: the console shows packets sent on every network interface and RAKSHA's own outbound calls. Pull the cable: the counter goes flat.
  • Per-run names: files RAKSHA places in a target use random names each run, so target code cannot detect and dodge the tests.

28Rules of engagement and the asset registry

LevelNameMay
R0Observescan and map only
R1Recommendtest in sandbox, prove, draft and gate fixes; apply nothing
R2Act with approvalstage a verified fix; apply after human sign-off
R3Act autonomouslyapply verified fixes within standing orders

The asset registry (raksha/data/assets.json) names each system, its mission function, owner unit and tier. The tier caps the level: mission-critical systems are recommend-only with two approvers. Risky patches (touching authentication or crypto) step down automatically. Unknown systems are treated cautiously.

29Risk and scoring

  • CVSS 3.1 score computed exactly from the finding; CVSS 4.0 vector recorded (its score table is not bundled, so no score is invented).
  • MITRE ATT&CK and D3FEND labels: the attacker technique a weakness enables and the matching defence.
  • Mission impact: severity weighted by the asset's tier.
  • Attack graph: how findings chain across the estate; the cheapest path is highlighted.
  • Calibration: each lane's trust is measured against ground truth, with confidence intervals.
Terms explained

CVSS: the standard 0–10 severity score for weaknesses. ATT&CK: MITRE's catalogue of attacker techniques. D3FEND: MITRE's matching catalogue of defences.

30Post-quantum readiness

Future quantum computers will break today's public-key cryptography. RAKSHA inventories every cryptographic primitive in the estate (where RSA, elliptic curves and weak hashes are used) and produces a migration plan to quantum-safe algorithms, shown on its own console screen.

Key takeaways
  • Two kinds of finding (read-only and run-the-code), one record, one gate.
  • The gate and the red team decide; the model only proposes.
  • Everything is sealed, signed, chained and replayable.

Part IV

Project memory and learning

Every project gets an identity and a signed, versioned history, so its owner can see their security any time, and the system learns which faults keep coming back.

31Project identity

Each project gets one ID for life, like PRJ-mixed-estate-36273DF0. It is recognised by its name and the shape of its files, not by where it sits on disk and not by file contents, so a patch never changes the ID and scanning from a different folder finds the same project. A different project with the same name gets its own ID.

Built

raksha/projects.py. Everything is stored on the box under RAKSHA_HOME (default ~/.raksha).

32Versioned reports

Each run writes the next report version: v1, v2, v3. Every version is signed and chained to the one before, like the journal. Nobody can quietly drop a finding between v3 and v4, edit an old report, or remove one; verification would fail for every later version.

33The colour-coded "what changed" report

MarkMeaningRule
✓ fixedGone since last versionOnly when the absence is itself a proof (a deterministic re-check no longer matches)
? not re-foundA crash not seen this runShown, but never counted as fixed
✚ newNot in the last versionIncludes anything a patch introduced
● still openIn both versionsWith how many versions it has been open
⚑ needs a humanRAKSHA may not or cannot close itWith the reason and a checklist

Colour never appears alone: every line carries an icon and a word, so the report works for colour-blind readers and on a black-and-white printout.

34Needs a human

ReasonWhy a person
Rotate a credentialOnly its owner can revoke and reissue it
Policy decisionWho may call an endpoint is the system owner's call
Dependency upgradeA prepared version bump needs a real build to verify
Crypto migrationChanging algorithms needs a key and data plan
Gate could not certifyProven weakness, no fix passed all five checks
Recommend-only assetThe fix is proven, but rules of engagement require approval

Each item comes with a checklist. When someone marks it done, RAKSHA does not take their word for it: the next run re-checks, and the report says "confirmed closed" or "still present".

35Score, deadlines, exposure-days, secrets, certificate

  • Posture score (0–100): 100 minus weighted open weaknesses (severity × asset tier). The breakdown always adds up exactly. Below the evidence floor it shows "n/a", never a guess.
  • Deadlines: each severity has a fix deadline (critical 7 days, high 30, …), tightened for mission-critical systems. Exposure-days counts how long each serious weakness has stayed open.
  • Secrets tracker: every leaked credential, whether it was rotated, and for how long it was exposed.
  • Data-handling statement: what was read, and the measured proof that nothing left the box during the run.
  • Attack-surface drift: a warning when a new version adds a network listener, file upload or privileged call, even before any bug is found.
  • Readiness certificate: a signed statement ("as of v7: no open critical weakness, all fixes proven, 3 items await a human"). Issued only when the record supports it.

36Self-learning

In plain words

RAKSHA studies its own history across projects. It counts which kinds of fault keep recurring, which fixed faults came back, and which unfamiliar libraries appear. From that it proposes guidelines for ACG and learns new things to watch for, but nothing it learns takes effect without proof or approval.

  • Recurring-fault analytics: by fault family, language, component and owner unit, with trends and regressions.
  • Guideline proposals for ACG: a fault family seen across two or more projects becomes a draft rule with evidence counts, anonymised examples and the proven fix pattern. It changes nothing until a named person approves it.
  • Learning new technology: unfamiliar libraries are logged; a lesson (for example, "treat this call as privileged") starts on probation.

37Keeping learning safe

  • Evidence counts only when it comes from a gate-verified record.
  • A lesson on probation applies only inside the project that proposed it. It is promoted only after three verified cases from at least two different projects.
  • One false alarm demotes a lesson at once, and the project that taught it is quarantined.
  • Every lesson keeps its full history, and any lesson can be rolled back with one click; the test suite proves rollback restores prior behaviour.

38Pre-merge check and compliance pack

Pre-merge check (python -m raksha.premerge PATH): developers run it before merging a change. It blocks on an approved guideline, on the return of a previously fixed weakness, or on anything critical. Compliance pack: a quarter's signed reports and certificates bundled as verifier media, so an auditor re-checks every signature and the chain on their own machine.

Not built · for the team

Three Wave 5 items are left to the team: an explainer of how a weakness could be reached (K21), answering questions about a project from its reports (K24), and a process drill on a copy of a project (K30). Generating them was stopped by an automated safety classifier during the build. Their specifications are in PLAN_V2.md, and the code they plug into exists.

Key takeaways
  • Every project has an ID and a tamper-proof, versioned history.
  • The report shows what changed, colour-coded, and what a human must do.
  • Learning proposes; proof and people decide.

Part V

The operator console (UI and UX)

One offline web page served from the box. Fourteen screens, English and Hindi, readable on a projector.

39Design principles

  • Offline: one self-contained page; no font, script or image from outside. The air-gap guard checks it.
  • Honest: every value comes from the record. If something was not measured, the screen shows a dash.
  • Glanceable: state is shown by colour, icon and word together.
  • Two voices: each finding can be read as a staff-officer summary or as engineer detail.
  • Bilingual: one key switches English and Hindi (हिन्दी).
  • Projector-ready: a high-contrast mode with heavier lines and larger text.

40Screen-by-screen tour

1 · Mission Board

Every target as a card: green (built and deep-tested), amber (build-free mode, still finding), red (could not read). Counts by status and the rules-of-engagement level per target.

2 · Live Pipeline

Findings flowing through suspected → confirmed → patched → verified, plus the ranked risk register: fix these first.

3 · Event Log

The run's story in plain sentences: "harness synthesized for parse_record", "candidate 2 rejected at CLEAN_REFUZZ", "VERIFIED; fix proven (template lane)".

4 · Finding Detail (the main screen)

Search, filter and sort; the five-check gate strip; split-screen replay (vulnerable build fires, patched build silent); the patch; red-team result; proofs; staff and engineer views; operator actions.

5 · Attack Graph

Findings as a graph of steps across the estate, with the cheapest path lit and each edge explained on hover.

6 · Estate Map

Targets by asset tier against status, and the top three risks.

7 · Post-Quantum

The cryptography inventory and the migration table: file, line, primitive, replacement.

8 · Evidence Vault

Pick any reportable finding and press Verify: every hash and the signature are re-checked live.

9 · Scorecard

The jury's measures, live: precision, findings, fixes, speed, model calls and tokens, cloud calls (0), sandbox status, what the run did not establish.

10 · Commander's Brief

A JSSD-style brief per finding, in English or Hindi, exportable as PDF (English).

11 · Demo Beats

Run the "it says no" sequence; ingest a judge's media with a live time-to-first-finding clock; the egress counter for the cable pull.

12 · Time-lapse

A slider over a recorded run's journal: findings, targets and what the system was doing at any moment.

13 · Projects

Every project's latest score and open items; per project the colour-coded "what changed", needs-a-human checklists with Mark done, version picker, English/Hindi one-page summary, readiness certificate, and developer / commander / auditor views; the mission view and posture over versions.

14 · Learning

Draft guidelines for ACG with Approve / Reject (a name is required), lessons with Roll back, recurring-fault analytics and unfamiliar libraries.

41Operator actions

Approve, reject, mark false positive, re-run the red team, export a bundle, issue an advisory, run the demo beat, ingest media, zero the egress counter, mark a needs-human item done, issue a certificate, decide a guideline, roll back a lesson. 49The sealed box

  • Hardware: one machine with a 32 GB GPU for the model; a CPU-only fallback profile exists.
  • Containers: the RAKSHA image (orchestrator and console), the sandbox image (where target code runs, no network), and the model server (vLLM) on an internal network with no route out. The console is published only to the machine itself.
