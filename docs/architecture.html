Part 0

The brief, and the bet

Everything downstream is a consequence of three things the brief implies but never says, and one bet about how to win with a weaker tool.

0.1

What the competition asks

Build a cyber-reasoning system — an LLM laced with fuzzers, static and dynamic analysis and a regression test harness — that autonomously finds a vulnerability, patches it, and proves the fix holds, pitched to run against customised Indian Armed Forces infrastructure.

Implication 1

Offline is non-negotiable

"Customised IAF infrastructure" means air-gapped. No cloud model, no pip install at runtime. This single constraint eliminates most of what a naive team would build.

Implication 2

The target is unknown

"Customised" means we cannot pre-study it. Unknown language, build system, source or binary, library or running service — until the finale.

Implication 3

Trust is the real currency

Software that autonomously changes Army systems is never accepted unless it can prove what it did and know the limits of its own authority.

0.2

Why the obvious approach fails

Point a big, smart AI at the code. It fails for two independent reasons, and the second is the one teams miss.

~34%

best frontier-agent patch rate on SEC-bench

~18%

best frontier-agent proof-of-vulnerability generation

~24%

best security detection model, F1 on a 25,440-function CVE benchmark

SEC-bench Pro, on real browser-engine bugs: strongest configuration ~32%, open-weight baseline ~12%, and the majority stay unsolved even with a 90-minute budget. Fine-tuning security models yields "calibration without comprehension" — more confidence, not more correctness. So "just use a smarter AI" is both unavailable (it lives online) and insufficient (nobody has solved this). If even frontier models fail two-thirds of the time, the winning move is not a bigger model. It is a better scaffold and an incorruptible verifier — we compete where the losses actually are.

0.3

The bet, and why a better model still helps

The central bet

Do not trust the AI. Make it prove everything.

The model guesses a fix. A strict mechanical inspector tests it: does the original attack still work? does every old behaviour still hold? does a fresh campaign find anything new? Only if every check passes does the fix count. The model can be weak, because the model is not the thing that decides what is true.

The resolution

The judge and the lawyer

The verifier is the judge — the verdict is final and cannot be bribed, but it does not investigate the case. The model is the lawyer — it builds the case for the judge to rule on. A better lawyer never overrules the judge, but walks in with a stronger case, so the judge says yes sooner and more often.

So the two halves improve different dimensions: the verifier makes us safe, the model makes us effective. Deterministic code is a floor on correctness; the model is the engine of discovery. This is also why test-time scaling is nearly free for us — sampling several candidate patches and letting the verifier pick adds roughly ten points, and our verifier already exists.

0.4

What is scored

The five-slide shortlisting stage is banked. Every remaining point comes from the finale five — so the operating rule for the whole build is that a criterion you cannot measure is a criterion you cannot score. No component is finished until it emits the number that proves it, while it runs.

Banked · shortlisting

Resource · Novelty · Lightweight

Already paid for by the deck. Still restated in the room, but no longer what the remaining work is optimising.

Live · finale

Performance · Speed · Precision

Bugs found and patched; median time-to-PoV and time-to-patch; how often we are right and how little noise we make.

Live · finale

Functionality · Scalability

Does the full loop run unattended; does it hold up across many targets and languages — language scalability, not thread count.

Part A

The system

Provenance is marked on every component, because the first thing a technical judge wants to know is what we built versus what we downloaded. TAKE use as-is · WRAP thin adapter · BUILD our work — exactly six of these are the novelty surface.

Fig 1

One spine, every language. The left margin marks the five layers: everything below Layer 1 is written once and runs for every language, which is the scalability claim in structural form. The two amber exits are the redundancy argument — each is still a real result.

We extend SARIF — the standard every static tool already emits — rather than inventing a format, so any tool's output can enter and ours can leave into anything that reads SARIF. The precision claim is not a tuning result; it is this state machine refusing a transition.

Cheapest check first, so a bad patch is refused for the least compute. Each candidate must earn all five itself — it never inherits a previous round's passes.

The model layer is a proposer, subordinate to the gate. Note what is taken away from it: localisation is deterministic, so the model is handed one function rather than asked to search a repo.

Fig 5

Nothing is trusted until it proves itself

This is the frame over the whole novelty surface, and the most defensible thing we can say in the room. One philosophy, enforced mechanically at five different levels — and we apply it to our own outputs, not just the target's code. The third instance closes a hole the dossier leaves open: the model writes the regression test that goes into the bundle and into the target's own suite, so a test that never actually failed on the vulnerable build would be a worthless proof — it has to earn its place like everything else.

Fig 6

Autonomy is not a switch. It is a per-asset authority level the system obeys, and it steps down on its own as the signals weaken — the same logic as fire control. An operator may always set it lower than the cap, never higher.

Fig 7

Four loops in the design; three claimed for the demo — the nightly QLoRA refresh is a real deployment feature but it will not visibly improve anything inside the finale, and saying so is worth more than implying otherwise.

The architecture will look similar across many teams — it is the template everyone's AI suggests. The room is won by what the jury can see. So demonstrability is an architectural requirement here, not a presentation afterthought: every novel mechanism needs an observable hook or it cannot be scored on novelty.

B.4

The honesty that itself scores

For a defence jury the most trust-building move is to state limits plainly. Volunteering the bound is what makes the headline numbers believable — and it is exactly the posture a signals authority needs before trusting software near a live system.

What we claim

  • 100% precision on reports, as a structural property — the data model forbids an unproven finding from being reported.
  • The gate proves "no observed behaviour changed across N inputs and M tests", with K flaky inputs quarantined and listed by name in the bundle.
  • We carry the most common dependencies offline.
  • Self-improvement demonstrated at the loop level — three online loops.
  • Every number comes from our own ARVO / AutoPatchBench baseline.

What we explicitly do not claim

  • Precision on patch semantic correctness. We do not claim formal equivalence, and we say so before being asked.
  • Nightly QLoRA as a 36-hour result — it is a deployment feature.
  • A complete dependency mirror. Anything missing degrades to static analysis, not failure.
  • That we fuzz a React front end. Its real attack surface is XSS, prototype pollution, client-side authz and vulnerable dependencies — so we run static and dependency lanes and point the fuzzing at the API behind it. Claiming otherwise would lose a technical judge.
  • That the authz oracle works unaided. It needs two principals on the target, supplied by the operator at ingest. The ingest form asks for them.
  • Any certainty above 95%, on anything.
Part C

What holds when it breaks

Our confidence does not come from the system always working. It comes from the system degrading instead of dying — so the thing to engineer is the fallback ladder, not the perfection.

C.1

The honest arithmetic

~36%

a flawless end-to-end live run: build and fuzz work (~70%) × find a real bug (~80%) × validated patch (~65%)

~85–90%

a convincing demo of something real, once the fallback ladder exists

36 → 85

the build-dependent / build-free split alone is what moves it. The highest-value engineering in the project, and the least glamorous

Context worth keeping in mind: competitors are at the same ~36% or lower, and most do not know it. Knowing our real number and designing for it is itself an edge.

C.2

The fallback ladder

RUNG 1Target will not build → build-free lanes: static, dependencies, secrets, config. Still real findings.
RUNG 2No harness can be synthesised → the gate still runs on any harness a human supplies; today the C, Python and Go demo targets ship none and are fuzzed through synthesized drivers.
RUNG 3Fuzzing finds nothing in time → static and dependency findings carry the demo. They were running in parallel, not after.
RUNG 4No patch validates → REPORT_ONLY: a proven vulnerability report, signed, with no patch claimed.
RUNG 5Our pipeline stalls → the OSS-CRS ensemble, running in parallel on the same target the whole time.
RUNG 6The live demo breaks entirely → the full run, recorded at a safe point before judging, narrated over.

Every rung is still a real, honest result. That is the whole point.

C.4

Kill-switches, decided in advance

The same discipline the product claims for itself, applied to the team: know the limits of your own authority, and decide the aborts while calm. Hour 30 is not calm.

Harness synthesis stalls on their target

No candidate driver passes the two-check quality gate → the build-free lanes still report, and a human-written harness drops into the same gate; say so openly.

LLM lane is not beating templates

By the checkpoint → demo templates as primary and the LLM as fallback. Still impressive, still honest, and it raises the zero-inference number.

Their target will not build

Switch to a bundled ARVO target and reframe as a portability demo. A working demo on target B beats a dead terminal on target A.

Anything in WOW slips

Cut it before it threatens core. A flawless core demo with three wow beats beats a broken attempt at five.

Make CORE flawless. Make a few WOW beats perfect. Describe the rest. Never let a nice-to-have break a must-have.

D.3

Described, not built

Legitimate, differentiating, and worth one slide each — and worth no finale build time. They are differentiators precisely because they answer operational questions (authority, rehearsal, mission impact) that a brief-literal competitor will not think to ask.

Red-vs-blue self-play

A red RAKSHA injects realistic bugs into clean code; blue must find and fix them. Unlimited offline training data, and a continuous measure of true recall — so we would know our real hit rate instead of guessing it.

Digital-twin rehearsal

Before any patch reaches a live system it runs against a sandboxed replica under replayed real traffic. A drill before the operation.

Mission-aware priority

Findings ranked not just by severity but by which unit and which mission depends on that system.

Terms

So this sheet can be read cold, by someone who is not a programmer.

CRS —
cyber-reasoning system; a program that reasons about other programs' security by itself. What the competition asks us to build.
Fuzzer —
bombards a program with thousands of malformed inputs to make it crash or misbehave.
Harness —
the small wrapper that feeds fuzzer bytes into the function under test. Often missing, sometimes written automatically.
Oracle —
anything that can tell you a bug just happened. A sanitizer is an oracle; so are our tripwires and the metamorphic check.
Sanitizer —
instrumentation that makes a silent bad action loudly abort, so it can be caught.
Reproducer / PoV —
a concrete input, or request pair, that triggers the bug. "No reproducer, no report" is our precision rule.
Overfitting patch —
a "fix" that silences the one test but secretly breaks normal use. What the differential corpus exists to kill.
Regression harness —
the project's own automatic "does it still work?" checks.
Verifier / gate —
the part that decides what is true. In our design, the brain.
Scaffold —
the reusable loop around the model that lets it act: read, edit, test, retry.
SARIF —
the standard format static analysis tools already emit. We extend it with a proof block rather than inventing a format.
CWE —
the standard catalogue of weakness types, e.g. CWE-89 is SQL injection.
Quantisation (Q4/Q5) —
shrinking a model to fit in memory. Lower number is smaller and faster, slightly less accurate.
AST delta —
how much of the code's structure a patch changed. Small is surgical and good; large is suspicious.
Attestation —
a signed statement of what was tested, by which version, with what result. Makes the evidence tamper-evident.
SBOM —
a machine-readable list of every component inside a piece of software.
Variant analysis —
after finding one bug, searching for the same mistake everywhere else. Our vaccine automates this from a verified fix.
Air-gapped —
physically disconnected from any network. Nothing can pip install or call a cloud model there.
JSSD —
the Indian Armed Forces' Joint Services house style for documents. Our Commander's Brief outputs in it.
ARVO —
~6,100 real bugs, each with a vulnerable build, a fixed build, a trigger and the gold patch. Our practice set, training data and ground truth.

Two invariants hold up everything above, and both are enforced by refusing a transition in the data model rather than by review or by promise. No reproducer, no report — a finding without one that actually replays can never leave SUSPECTED. Nothing unproven ships — a patch reaches VERIFIED only with all five checks passed and evidence the original attack is dead, each candidate earning all five itself. That is the difference between a system that claims precision and one that could not produce an unproven report even if it were asked to.
